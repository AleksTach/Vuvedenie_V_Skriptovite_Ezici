# Отговори към задачата за `threads_race.py`

**Тема:** Python threads, GIL, race conditions и multiprocessing

## 1. Сравнение между sequential и parallel режим

При изпълнение на оригиналната версия на програмата, в която всяка стъпка използва `time.sleep()`, бяха получени приблизително следните времена:

| Режим | Време |
|---|---:|
| Sequential | `14.22s` |
| Parallel | `3.20s` |

Parallel режимът завършва значително по-бързо, защото `time.sleep()` не е CPU-bound операция. Докато една нишка е в `sleep`, тя не изпълнява Python байткод и освобождава GIL-а. Това позволява на друга нишка да продължи изпълнението си.

Следователно петте коня не чакат един след друг, а чакането им се припокрива. Затова общото време е близко до времето на един кон, вместо до сумата от времената на всички коне.

**Извод:** Threads са ефективни при I/O-bound задачи или задачи с изчакване, защото GIL не блокира полезното припокриване на чакането.

## 2. Премахване на `print_lock` в `draw_row()`

Ако се премахне:

```python
with print_lock:
```

от функцията `draw_row()`, няколко нишки започват да пишат едновременно в един и същ изходен поток: `sys.stdout`.

Визуално това води до следните проблеми:

- редове се презаписват;
- ANSI escape кодовете се смесват;
- progress bar-овете се слепват;
- конете изглежда, че прескачат между различни редове;
- части от различни съобщения се появяват на едно и също място.

Причината е race condition върху споделен ресурс: терминала. Всяка нишка се опитва да мести курсора, да изчисти ред и да отпечата ново съдържание. Без lock няма гаранция, че тези операции ще се изпълнят като една цяла, непрекъсната операция.

**Извод:** Lock-ът е нужен, когато няколко нишки използват общ ресурс и операцията трябва да остане атомарна от гледна точка на програмата.

## 3. Замяна на `time.sleep()` с CPU-bound натоварване

Ако в `run_horse()` заменим:

```python
time.sleep(random.uniform(0.02, 0.12))
```

с:

```python
sum(i * i for i in range(200_000))
```

задачата вече става CPU-bound. При измерване без терминалната анимация бяха получени приблизително следните времена:

| Режим | Време |
|---|---:|
| Sequential CPU | `4.34s` |
| Threaded CPU | `4.46s` |

В този случай threaded версията не е по-бърза. Дори е малко по-бавна заради допълнителните разходи по създаване, превключване и управление на нишките.

Причината е GIL-ът в CPython. Той позволява само една нишка в рамките на един процес да изпълнява Python байткод в даден момент. CPU-bound изчислението изпълнява Python код почти през цялото време, затова нишките не могат реално да използват няколко CPU ядра паралелно.

**Извод:** Threads не ускоряват чисто CPU-bound Python код в CPython.

## 4. Използване на `multiprocessing.Process`

Когато `threading.Thread` се замени с `multiprocessing.Process` при същото CPU-bound натоварване, резултатът беше приблизително:

| Режим | Време |
|---|---:|
| Multiprocessing CPU | `1.30s` |

Това вече е по-бързо от sequential версията, защото всеки процес има собствен Python interpreter и собствен GIL. Операционната система може да разпредели отделните процеси върху различни CPU ядра.

Разликата е следната:

| Threads | Processes |
|---|---|
| Един процес | Няколко отделни процеса |
| Един Python interpreter | Отделен Python interpreter за всеки процес |
| Един GIL | Отделен GIL за всеки процес |
| Няма истинско CPU паралелизиране за Python байткод | Възможно е реално паралелно CPU изпълнение |

**Извод:** За CPU-bound задачи multiprocessing е подходящ избор, защото заобикаля ограничението на GIL чрез използване на отделни процеси.

## 5. `race_parallel()` с `ThreadPoolExecutor`

Функцията `race_parallel()` може да бъде пренаписана с `concurrent.futures.ThreadPoolExecutor` така:

```python
from concurrent.futures import ThreadPoolExecutor


def race_parallel() -> None:
    sys.stdout.write("\033[2J\033[H")
    print("PARALLEL: all horses racing at once\n")
    finishers: list[str] = []
    finish_lock = threading.Lock()
    start = time.time()

    with ThreadPoolExecutor(max_workers=len(HORSES)) as executor:
        futures = [
            executor.submit(run_horse, i + 3, name, finishers, finish_lock)
            for i, name in enumerate(HORSES)
        ]

        for future in futures:
            future.result()

    sys.stdout.write(f"\033[{len(HORSES) + 5};1H\n")
    print(f"Elapsed: {time.time() - start:.2f}s")
    print(f"Finish order: {' -> '.join(finishers)}")
```

В сравнение с ръчното използване на `threading.Thread` се спестяват около четири реда код, защото вече не е необходимо ръчно да се извикват `start()` и `join()` за всяка нишка.

По-важното предимство е, че `ThreadPoolExecutor` работи с `Future` обекти. Извикването на:

```python
future.result()
```

връща резултата от задачата или повдига exception, ако задачата е завършила с грешка.

**Извод:** `ThreadPoolExecutor` прави кода по-кратък, по-четим и по-надежден при обработка на грешки от worker нишки.

## 6. Какво се случва при exception в една нишка?

Ако един кон "крашне", например чрез exception по средата на цикъла, спира само неговата нишка. Останалите нишки продължават да изпълняват своите задачи.

При обикновен `threading.Thread`:

- exception-ът се отпечатва в конзолата;
- main thread-ът не спира автоматично;
- останалите нишки продължават;
- `thread.join()` само изчаква нишката да приключи;
- `join()` не връща exception и не казва дали нишката е приключила успешно.

Това означава, че `join()` не е надежден механизъм за засичане на провалена нишка. Той е механизъм за изчакване, не за проверка на резултат.

Надежден начин за засичане на грешка е worker функцията да се обвие в `try/except` и exception-ите да се записват в споделен списък или queue.

По-удобен вариант е използването на `ThreadPoolExecutor`:

```python
future = executor.submit(run_horse, ...)
future.result()
```

Ако `run_horse()` хвърли exception, `future.result()` ще го повдигне отново в main thread-а. Така грешката може да бъде хваната и обработена надеждно.

**Извод:** `thread.join()` не съобщава за exception в нишка. За надеждно засичане на провалени нишки е по-добре да се използват `Future` обекти или изрично събиране на грешките чрез `try/except`.
